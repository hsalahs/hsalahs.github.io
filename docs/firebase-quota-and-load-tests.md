# Firebase read quota, estimates, load tests and alerts

_Moved out of CLAUDE.md (nothing was removed). Read this when: before anything that adds Firestore reads/writes, when the free Spark limits (50k reads, 20k writes per day) matter, for capacity questions (how many guests / events per day), the quota email alerts, the real load tests and the kept test event._

- **Blaze (paid) is not available to the user**: billing addresses in Saudi Arabia must go through the reseller CNTXT and need a commercial registration. Stay on Spark (about 50k reads/day for the whole project; when it runs out everything stops until the daily reset).
- The user already hit the limit once with ~700 guests and many refreshes.
- **Done:** (1) persistent local cache in `firebase-init.js`. (2) the guest's barcode code is now its own Firestore document id (event.html's three guest-creation paths), so scan.html checks a guest in with one direct `doc()`/transaction, no collection read, no live listener on `guests` at all. (3) the scanner's "تم الدخول: X / Y" counter reads `events/{id}.guestCount` / `.scannedCount` via one cheap document listener (`startEventCounterWatch` in scan.html); `scannedCount` is bumped in the same transaction as the guest's `scanned` flip, and `firestore.rules` has a matching `hasScanSession`-only, +1-only rule for it.
- (4) scan.html reuses the device's saved names list (localStorage, `loadedAt`) for 3 hours instead of `getDocs` on every open; "🔄 تحديث القائمة" forces a download.
- **Read estimate (done, computed from the code + Firebase billing rules — the emulator doesn't count billed reads):** event day with 80% attendance, 4 door phones × 3 opens, 3 dashboard opens. Before (4): 1000 guests ≈ 26k reads, 5000 ≈ 131k. Biggest costs at 5000: scanner list loads 60k, check-ins ~8 reads each (incl. rules get()s) 32k, counter listener fan-out 20k, dashboard 19k. Told the user: don't promise more than ~2000 guests per event on Spark, and check before two big events on the same day.
- (5) **Roster document** `events/{id}/roster/list` = `{guests: ["id|scanned|name", ...], updatedAt}`, written by event.html (`writeRoster`, throttled 30s, only from server snapshots, skipped above 900 KB) and read by scan.html's `loadGuestsOnce` in 1 read; falls back to `getDocs(guests)` when missing or unreadable. Rules: read = admin/owner/scan session; write = admin/owner, doc id `list`, keys `guests`+`updatedAt`. Deleted with the event (before the event doc).
- **Read-cost cuts (Oct 2026):** (1) event.html's `backfillRequestGuestIds()` (a plain `getDocs` over all approved requests on every dashboard open, up to 300 billed reads) was removed: it only repaired requests approved before `guestId` was copied onto them, and no real customer events predate that field (all old events are tests). `approveRequest` still writes `guestId` in its transaction; invite.html shows "preparing" for an approved request without one. The scanner roster already follows every name change through the dashboard's guests listener, so extra explicit `scheduleRosterWrite()` calls after import/approve/manual add were tried and dropped (no gain, small stale-write window). Tests: 442 page tests.
- **Still proposed, not built:** the scanner counter polled every 30s instead of a live listener (recommended against for now: it slows the counter for every event to save reads only on big ones). Check-ins (~8 reads each) can't shrink without weakening security.
- **Real-Firebase check of the backfill removal (Oct 2026):** on the kept test event (500 guests + 100 approved requests) a real browser opened the dashboard against real Firebase with the old and the new event.html: 606 reads vs 505 (exactly one read per approved request saved per open), same 500 guest rows. Updated 700-guest estimates against the official Spark limits (50,000 reads / 20,000 writes / 20,000 deletes per day, 1 GiB, 10 GiB/month egress; the day resets around midnight Pacific, about 10:00 Saudi time): no link to guests (all cards made by the owner in one click, nothing read by guests) about 6.4k reads on the event day, 10k worst case (13-20%); link to 300 + 400 added by the owner about 9k reads on a registration day and 6.4k on the event day (18% / 13%, worst cases 20% / 23%); writes under 10%. Dashboard opens are the thing that multiplies cost (30 cold opens would be about 40% of the day); the quota is shared by all customers.
- **If we ever leave the free plan (Blaze):** much of the read-saving work exists only because of the Spark quota (the roster document, the 3-hour saved names list in scan.html, the 30 s roster throttle, the no-listener-on-guests scanner design, the removed request backfill, the one-big-event-per-day guidance). Revisit and simplify those then (some, like `increment(1)` for the counter, are correctness fixes and must stay). Blaze is not available to the user today (Saudi billing, see the quota section).
- **Real load test (Oct 2026, 500 guests, done):** run from the sandbox with the real Firebase JS SDK in Node (`firebase@10.12.0` + undici ProxyAgent, `experimentalForceLongPolling`), the same transactions and listeners as the pages; reads measured from Cloud Monitoring (`firestore.googleapis.com/document/read_count`, 60 s buckets, with the Firebase CLI's access token, read-only; it expires after about an hour, `npx firebase-tools projects:list` refreshes it; the Firebase console charts are UTC+3). Setup: a throwaway customer account + event created over REST, the user activates it as admin (guestLimit 500). Scripts lived in the session scratchpad, not in the repo. Results: import of 500 guests 10 reads (10 transactions of 50); dashboard open ≈ N reads each (Node has no persistent cache, so 3 opens ≈ 1.5k is a worst case); 4 door phones entering ≈ 30; check-ins ≈ 6 reads each (≈ 2.35k for 400 check-ins + 80 re-scans, before the increment fix saved about 1 read each); total for 500 guests ≈ 3.9k reads (8% of the 50k day), so the earlier 8-10k estimate was too high; 5000 guests extrapolates to about 40k (one big event per day). The first run found the concurrent check-in bug (see "Concurrent check-ins"): 8% denied at about 1 scan/s, about 150 of 400 at about 10 scans/s; after the fix (#132) 0 failures in 400 paced check-ins and 100 fast ones, scannedCount exactly 500. The second run's read total (7.0k) was inflated by the user's own admin dashboard being open (listener spike when guests were added and after the test), so it was rerun on the kept event with the admin panel closed (clean run, after the increment fix): total 4.2k reads for 500 guests (dashboard 3 opens 1.5k, door phones entering 24, 500 check-ins + 80 re-scans 2.6k ≈ 4.5 reads per scan, down from ≈ 6.4), 0 failed check-ins in 400 paced + 100 fast ones, scannedCount exactly 500.
- **Quota email alert (Oct 2026):** a Cloud Monitoring alert policy "Firestore reads: nearing the 50,000/day free limit" (`projects/wedding-qr-16d01/alertPolicies/5205822055863507242`) emails the founder (notification channel "Founder email (quota alerts)", the admin address) when Firestore document reads in the last 24 hours (rolling, so a little more cautious than the real quota day that resets about 10:00 Saudi time) pass 35,000 (70%) or 45,000 (90%). Created through the Monitoring API with the Firebase CLI token on the founder's approval (works on Spark, no billing needed); delete or edit it in Google Cloud console > Monitoring > Alerting (https://console.cloud.google.com/monitoring/alerting?project=wedding-qr-16d01). A second policy "Firestore reads: spike in one hour (above 8,000)" (`alertPolicies/18065326584232970734`, same email channel, 1 hour window) catches sudden spikes (a normal 700-guest wedding hour is about 2-3k). Because the 24-hour window is rolling, the day after a heavy day (tests, a big wedding) it can still show a high number even though the real quota day has reset; check the Usage tab before reacting. The test email has not been sent (usage never reached the threshold). Why not a script: a Claude session is not continuous and the CLI login expires; Spark has no built-in quota alerts, this is the free substitute.

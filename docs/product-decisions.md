# Product decisions and customer-facing features

_Moved out of CLAUDE.md (nothing was removed). Read this when: before changing or adding any customer-facing feature, wording, pricing, event/guest rules, the invite link, WhatsApp messages, the guide, or when a question starts with "why did we decide ..."._

- **Guest limit:** free events hold 5 guests. The admin activates an event and sets its guest limit (`paid:true`, `guestLimit:n`); customers cannot set these (rules enforce it, including the "bump guestCount" requirement). Prices are agreed on WhatsApp, not in the app.
- **Theme:** five palettes (gold, rose, emerald, sapphire, ivory). The dashboard and invitation follow the theme; the scanner follows the accents only and stays dark. The QR itself is always black on light.
- **Not building:** a "plan label", and the human services (event-day support, field supervisors).
- **Pricing stays custom (user's call):** prices differ by country (Saudi now; UAE and Egypt next) and are agreed on WhatsApp. The landing page says "السعر حسب عدد ضيوفك" with three steps (try free → ask on WhatsApp → pay and get activated) — no amounts, no payment method, no activation time. The hero (next to "ابدأ الآن") says "أول 5 ضيوف مجانًا — وأكثر من كذا نرسل لك عرض سعر، ونفعّل مناسبتك بعد الدفع" and its WhatsApp button is "اطلب سعر مناسبتك" (`data-wa="quote"`, message asks for a quote with the guest count) — from the VibeQuality audit's conversion item; an audit will likely keep flagging "price only via contact" while there are no amounts, which is the accepted cost of custom pricing. Never publish packages with features the site doesn't have (a suggested Basic/Standard/VIP list was rejected: WhatsApp sending, per-event domains, VIP cards, single shared QR, day-of staff, "unlimited guests"). Saudi market reference (Oct 2026): roughly 2–5 SAR per guest (My Event 100 guests/300 SAR, Asfrt 25/125, Da3wa ~$1.36/guest).
- **VIP guests (done):** `vip: true` on a guest doc, toggled from the row's ⋮ menu (`toggleGuestVip`, a plain owner update — no rules change). event.html: gold "★ VIP" badge + faint gold row; `buildGuestCard` draws a dark card with a double gold frame and a ★ VIP pill under the date, shifting the rest down 56px (QR box stays black on white). scan.html reads `vip` inside the check-in transaction and shows a "★ VIP" flag on the allowed/duplicate result. Not in the roster/offline list or Excel import (Excel column suggested for later).
- **Readable event link (done, #105):** `da3wt.com/<slug>` (English letters, digits, `-`, 3–40 chars; `SLUG_RE` + `RESERVED_SLUGS` in utils.js, same list in the rules). Set from event.html's edit card ("رابط الدعوة المخصص"); `setEventSlug()` claims `slugs/{slug}` = `{eventId, ownerUid, createdAt}` in a transaction (first come, create-only, public get) and releases the old one; deleting the event deletes its slug. **Automatic name:** the first time the owner opens the dashboard and the event has no `slug` field, `autoClaimSlug()` claims `slugFromName(name)` (utils.js: Arabic spelled in English letters, e.g. زفاف → zfaf, حلا → hla; English/digits kept; 3–34 chars), trying `-2`, `-3`, `-4`, then a random suffix; silent on failure; skipped for the admin viewing someone else's event; `slug: ''` (cleared by the owner) is never refilled. Done on dashboard open rather than at creation because the slugs create rule `get()`s the event, which doesn't exist yet inside the create transaction (would need `getAfter` = a rules change). `404.html` (GitHub Pages serves it for unknown paths) forwards `/name` to `invite.html?s=name`, which resolves the slug and shows `/name` in the address bar. Per-guest "send on WhatsApp" button: cancelled for now.
- **Guest name order (Oct 2026):** `sortGuestsByName()` (utils.js) puts all-digit names first in numeric order, then sorts the rest with `localeCompare(…, 'ar', { numeric: true })`, so names ending in a number sort by that number (ضيف 2 before ضيف 10) in the dashboard list, the attendance report and the exports that use it. Found when the user opened the 500-guest test report and saw ضيف 1, 10, 100, 101… instead of 1, 2, 3….
- **Guest ⋮ sheet (done):** the row's ⋮ (`.more-btn`, aria-label "خيارات") calls `openGuestSheet(docId)`, which fills the single `#guest-sheet` (name + VIP badge, code, attended or not) with "تمييز كـ VIP"/"إلغاء تمييز VIP" (`.gs-vip`), a red "حذف الضيف" (`.gs-del`, still goes through `deleteGuest`'s confirm) and "إلغاء". Slides up from the bottom on phones, centred above 600px; backdrop click and Escape close it. Replaced the old inline dropdown that opened below the row (users had to scroll to find it).
- **guide.html FAQ** covers: VIP, changing the automatic link, a deleted guest freeing a slot, a stuck "جاري التحميل...". Keep the guide in step with every customer-facing feature (user's standing request).
- **Deferred (user asked to keep it for later):** a pre-launch review of the visitor-facing pages (index, guide, invite) — a list of things worth fixing, no edits before approval.
- **Deferred:** guest-row avatar circles (first letter, green when checked in) — mocked up and liked, held back because the row got crowded next to the guest number; time / organizer / notes fields, party-size cards and open registration, App Check (no budget), landing "install hint".
- **Event type (done):** `type` on the event doc = wedding / graduation / event (`EVENT_TYPES` + `eventTypeOf()` in utils.js; missing = wedding, as before). app.html's create form has a required 3-button picker (`#ev-type-picker`, `pickEventType`, no default); until picked, the name placeholder cycles through the kinds' examples, then fixes to the picked one's. A new event starts with the kind's theme (wedding gold, graduation sapphire, event emerald — same as the demo); the owner can change colour and kind (edit card `#edit-ev-type`, `pickEditType`; changing kind leaves the colour). invite.html: the splash markup is the neutral logo; its inline script paints the demo's kind, or for a real invite the kind this device saw last for that link (`localStorage inv_kind_<eventId | s:slug>`), else the logo; `showInviteKind(type)` (called in init when the event loads) fades the right one in and remembers it, and the splash hider hides once the event data arrived, ≥1.6s after start and ≥1.2s after the kind faded in, never later than 3.5s (see Splash batch). No rules change (create rule has no key whitelist).
- **Domain:** `da3wt.com`, registered via Sahara Net — done (see above). Registrar portal: Registrar Lock is on, auto-renew is on, ICANN verification done.
- **guestCount can now decrease:** deleting a guest frees up their slot (business decision — the cap means "current guest count", not "total ever added"). `event.html`'s `deleteGuest()` does this in a transaction (delete + decrement together); `firestore.rules` has a matching owner-only, -1-only rule next to the scannedCount one.
- **guestCount-decrement loophole — decided: accept and monitor (user's call).** The decrement rule is NOT tied to an actual guest deletion, so a technically savvy customer could lower the counter via dev tools and add more guests than agreed. The user will watch for it instead: open the customer's event as admin — "عداد الضيوف" above the agreed limit means tampering — then deactivate the event or lower its limit. Don't re-propose closing it unless the user brings it up.
- **Company cloud server (under discussion):** the user's employer offers employees a free cloud server and allows personal commercial projects. Recommendation given: don't move the site or database onto it (GitHub Pages + Firebase are free; a server doesn't lift the Spark read quota unless the database moves, a big rewrite; it's tied to the job). Possible small helpers if wanted: daily Firestore backup, door-code rate limiting, deleting customer sign-ins (Admin SDK). Specs given: 1–2 vCPU, 2 GB RAM, 30–40 GB SSD, Ubuntu 24.04 LTS, static public IP (for a full move: 2 vCPU / 4 GB / 50 GB).
- **Floating WhatsApp button (index + guide only):** `a.wa-float`, fixed bottom-right (above the safe area), always visible while scrolling (user's choice — like the reference site they showed), green round button with the WhatsApp logo. Messages: index "السلام عليكم، عندي سؤال عن خدمة دعوات.", guide "…عن استخدام دعوات." (`data-wa="float"`; each WhatsApp link on a page has its own message). Not on app/event/invite/scan. User said they'll roll it back at once if it doesn't look right.
- **WhatsApp share message (Oct 2026):** event.html's share button next to the invite link opens `#share-modal` "معاينة رسالة الواتساب": a WhatsApp-bubble preview of `buildShareMessage(ev, link)` (utils.js: `*icon title ✨*` bold title per kind from `EVENT_TYPES` — 💌 دعوة زفاف / 🎓 دعوة حفل تخرج / 🎟️ دعوة فعالية — then الحفل/الفعالية name, Gregorian date, place, map link, the welcome line, and "🔗 أكّد حضورك واستلم بطاقة دخولك (QR):" + the invite link), an editable welcome line (`#share-welcome`, max `WELCOME_MAX` 400 so the wa.me URL works on every phone, counter), a green "مشاركة عبر الواتساب" (`https://wa.me/?text=` + encodeURIComponent — free, opens the owner's own WhatsApp) and "مشاركة بطريقة ثانية" (the old native share). The welcome is saved as `welcomeMessage` on the event ('' = the kind's default, `welcomeOf(ev)`); invite.html's RSVP card shows the kind title (`.inv-kind`) above the name and the same welcome (`.inv-msg`). Decided with the user: Gregorian date only; no groom/bride/family/time fields (event name is enough); no spaced-out letters "د عـ و ة" (break on some phones). User asked to keep a rollback ready if they don't like it.
- **Input length limits:** event name 80, venue 100, map link 300 (`maxlength` in app.html's create form and event.html's edit card; longer existing values stay as they are). A rules-level `welcomeMessage` length cap was deliberately deferred (the client caps it at `WELCOME_MAX` 400). A failed welcome save now shows a toast.
- **RSVP expectations on invite.html:** under "تأكيد الحضور" a dashed note (`.rsvp-note`): "بعد تأكيد حضورك، تتم مراجعة طلبك من {approver}. بعد الموافقة تظهر لك بطاقة الدخول (الباركود) هنا في نفس الرابط."; the pending screen says "تم إرسال طلبك ✅ بانتظار موافقة {approver}" + "افتح نفس الرابط من نفس الجوال" (`.pend-note` — the request is found by this device's localStorage). `EVENT_TYPES.approver`: wedding صاحب الدعوة, graduation منظّمي الحفل, event منظّمي الفعالية (not "مشرفي المدرسة": a graduation party is often held by a family).
- **Deleting a checked-in guest:** `removeGuestDoc()` in event.html first un-checks them in (scannedCount -1), then deletes (guestCount -1) — two transactions, because the rules only allow a guestCount drop in a write touching nothing else.
- **`users/{uid}` collection:** every signup mirrors itself into Firestore (email + createdAt, written once in `app.html`'s `submitAuth()`) — Firebase Auth alone keeps no record the client can list, and the admin's old "events only" view showed nothing for an account that never created an event or deleted it. `app.html`'s admin view has a "كل الحسابات المسجّلة" panel reading it — collapsed by default; the badge is a `getCountFromServer` count, and the list (with an email search) is read once, only when the admin opens it. `firestore.rules`: owner can create only their own doc with exactly `{email, createdAt}`; only the admin can read or delete it. The admin's 🗑 on a row (`deleteAccountRecord`) removes only that record — the customer's sign-in and events are untouched; deliberately no "clear all". Each account row also shows its status from the events already loaded (`accountStatus(uid)`, no extra reads): event count + "✓ مفعّلة (N ضيف)" / "يجرّب مجانًا" / "بدون مناسبة", with filter chips (الكل / عندهم مناسبة مفعّلة / يجرّبون / بدون مناسبة); tapping a row sets `ownerFilter` so the events list shows only that customer's events (bar with "عرض الكل"). Admin-only, so not in guide.html.
- **Rejected: a generic "/admin/users with roles, suspend, delete via server functions" spec** (Lovable/Supabase style). No server on Spark; the rules already enforce admin-only server-side; one admin, so no roles. Suspending or deleting a sign-in is done in the Firebase Console (Authentication → user → Disable / Delete account), which is free.
